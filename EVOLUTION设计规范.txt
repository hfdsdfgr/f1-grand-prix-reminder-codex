你现在需要重新设计并实现 GrandPrixReminder 的 Evolution（赛车演进）界面。

在开始修改代码前：

1. 先阅读项目现有的 development.md、DATA_ARCHITECTURE.md、design.md（如果存在）以及 Evolution/3D 相关现有代码。
2. 检查当前项目结构、数据模型、3D Renderer 和交互实现。
3. 如果项目中存在 frontend / uiux 等相关 Skill，请优先调用这些 Skill 辅助分析和实现。
4. 不要直接推翻现有实现。优先复用已有组件、数据层、路由和交互逻辑。
5. 当前 3D Prototype 的拖拽旋转手感已经确认满意，禁止重新设计 Rotation Interaction。替换模型、Renderer 或 UI 时必须尽可能保持当前旋转、缩放的操作手感。
6. 先给出简短实施方案，确认哪些现有模块可以复用，再开始修改。

==================================================
一、PRODUCT GOAL
==================================================

Evolution 不是普通的“赛车 3D 展示器”。

它的核心目标是让普通 F1 车迷直观理解：

1. 一台 F1 赛车由哪些主要部件组成；
2. 每个部件有什么作用；
3. 同一车队不同代际赛车发生了什么变化；
4. 同一辆赛车在一个赛季中发生了哪些重要升级；
5. 用户能够通过 3D 交互直接看到这些变化发生在哪里。

最终体验应接近：

Interactive F1 Engineering Archive

而不是：

- 3D 游戏
- CAD 查看器
- F1 数据 Dashboard
- 新闻页面
- 复杂工程仿真软件

整体继续符合 GrandPrixReminder：

Race. Debrief. Evolution.

==================================================
二、DESIGN LANGUAGE
==================================================

整体视觉方向：

Minimal / Motorsport / Technical / Premium

参考苹果官网、现代工业设计网站、汽车 Configurator 和工程产品展示页的克制感。

主要使用：

- 白色 / 浅灰背景
- 大量留白
- 黑色 / 深灰文字
- 极少量强调色
- 车队颜色作为局部视觉识别
- 细分隔线
- 清晰 Typography Hierarchy
- 轻量阴影
- 精确对齐
- 大面积 3D 内容区域

禁止：

- AI 紫色/蓝色渐变
- Neon
- Glow
- Cyberpunk HUD
- 大量半透明玻璃组件
- 到处都是圆角 Card
- 每个区域都加边框
- 大面积渐变
- Emoji 式技术标签
- 密集 Dashboard
- 过度动画
- 为“科技感”增加没有功能意义的装饰

科技感应该来自：

3D 空间运动
+
赛车拆解
+
部件关系
+
信息层级
+
演进对比

而不是 RGB / HUD / Glow。

==================================================
六、3D MODEL POSITIONING
==================================================

取消此前高模方案。

3D 赛车采用：

Refined Low-Poly / Lightweight Realtime Model

精细程度参考已经提供的 Sketchfab Low Poly F1 赛车截图。

不要追求：

- F1 游戏级高模
- CAD 精度
- 毫米级空气动力学细节
- 完整动力单元
- 内部机械结构
- 螺丝
- 管线
- 传感器
- 极端细小导流结构

但必须明显优于当前方块/Cuboid Prototype。

用户在手机正常观察距离应该能够清楚识别：

- Front Wing
- Nose
- Front Suspension
- Front Wheels
- Halo
- Cockpit
- Sidepods
- Floor
- Engine Cover
- Rear Suspension
- Rear Wheels
- Beam Wing
- Rear Wing

重点是：

轮廓正确
+
结构清晰
+
适合交互
+
轻量运行

而不是几何复杂度。

==================================================

==================================================

不要为每个车队、每个赛季完全重新建立一套独立模型体系。

采用：

Universal F1 Base Architecture
+
Team Material / Livery
+
Generation Component Configuration

逻辑：

Universal F1 Model

├── Shared Structure
├── Component IDs
├── Interaction Anchors
├── Materials
├── Team Theme
└── Replaceable Components

车队之间首先通过：

- Primary Color
- Secondary Color
- Carbon Areas
- Accent
- Material

形成视觉区别。

例如：

Red Bull：
深色主体 + 红/黄 Accent

Ferrari：
红色主体 + Carbon

Mercedes：
银 / 黑

McLaren：
橙 + 黑

第一阶段不需要精确复制 Sponsor Logo 和官方完整 Livery。

不要因为颜色不同复制整个模型文件。

==================================================

例如：

├── floor_RB19
└── engine_cover_RB19

RB20
├── base_car
├── front_wing_RB20
├── sidepod_RB20
├── floor_RB20

只对：

肉眼可观察
+
技术意义明显
+

的部件制作差异。

不要为了“看起来不同”而虚构结构差异。

不同技术规则时代允许创建新的 Base Architecture。

不要强行让所有历史 F1 赛车共享完全相同的几何底模。

==================================================
十二、COMPONENT LABEL SYSTEM
==================================================

删除当前所有 Label 指向左下角的实现。

改为：

Dynamic Technical Callout Layout

标签围绕赛车自然分布。

例如：

Front Wing ─────╲             ╱──── Rear Wing

Suspension ──────╲           ╱──── Engine Cover

                   3D CAR

       Floor ─────╱           ╲──── Sidepod

Label Placement 根据：

3D Anchor
→ Screen Projection
→ Available Screen Region

动态计算。

赛车旋转/缩放后重新计算。

要求：

- 尽量避免 Label 重叠
- 避免文字被连接线穿过
- 尽量减少 Line Crossing
- 尽量避免连接线穿过整辆赛车
- 标签保持短
- 使用细线
- 不使用巨型 Card
- 不使用 Neon
- 不使用游戏 HUD

当空间不足时允许减少非重要标签，而不是强行显示全部标签。

==================================================
十三、COMPONENT SELECTION
==================================================

用户点击赛车部件：

1. Highlight Selected Component
2. De-emphasize Other Components
3. Camera 可进行轻微 Focus
4. 显示 Component Detail

不要只显示：

“已选择：Front Wing”

Component Detail 使用：

Component
├── What is it?
├── What does it do?
├── Why does it matter?
└── Evolution / Current Specification

例如 Tyre：

Tyre

What is it?
赛车与赛道直接接触的部件。

What does it do?
负责传递纵向和横向力。

Key Factors
- Compound
- Temperature
- Wear
- Pressure

Evolution
显示当前车型/当前规格相关变化。

基础 Component Knowledge 必须来自人工审核的静态知识库。

不要每次点击部件调用 LLM。

AI 只用于有来源的动态升级信息、采访提炼等场景。

二十五、PERFORMANCE
==================================================

性能优先。

要求：

- Lightweight GLB/glTF
- Low-Poly
- Reasonable texture resolution
- Lazy load
- Cache model assets
- 不同时加载大量历史赛车
